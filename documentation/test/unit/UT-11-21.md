**Description:**
This suite verifies that all analyzers (`bandit`, `dodgy`, `mypy`, `semgrep`, `vulture`) correctly execute on known vulnerable test files and **persist their findings in the database**.

Each analyzer must mark its `Run` record as **COMPLETED**, set the correct `findings_count`, store findings, and maintain an accurate `severity_counts` dictionary. The tests also ensure **no unexpected findings** appear beyond the known expected results (`EXPECTED_FINDINGS_<TOOL>`).

**Preconditions:**

- Functional Django environment with all analyzers configured.
- Local or CI database accessible for persisting analyzer results.
- Known vulnerable sample files present:
  - `bandit_ringer_test.py`
  - `dodgy_ringer_test.py`
  - `mypy_ringer_test.py`
  - `semgrep_ringer_test.py`
  - `vulture_ringer_test.py`
- Each analyzer defines its `EXPECTED_FINDINGS_<TOOL>` constant.
- `Run` model includes persistence fields:
  - `Finding` model
  - `severity_counts` (JSONField)
- All analyzers initiated with `Run.Status.REQUESTED` and finalize as `Run.Status.COMPLETED`.

**Test Data:**

| Field             | Example Value                                   | Notes                                   |
| ----------------- | ----------------------------------------------- | --------------------------------------- |
| Analyzer Names    | `bandit`, `dodgy`, `mypy`, `semgrep`, `vulture` | One per test method                     |
| File Name Pattern | `sample_files/<tool>_ringer_test.py`            | Matches each analyzer’s vulnerable file |
| Initial Status    | `Run.Status.REQUESTED`                          | Analyzer starts as queued               |
| Expected Status   | `Run.Status.COMPLETED`                          | Should complete successfully            |
| Expected Findings | `len(EXPECTED_FINDINGS_<TOOL>)`                 | Used to validate persistence accuracy   |
| Comparison Metric | `(rule_id, line, column)`                       | Tuple-based accuracy check              |

**Execution Steps:**

### Analyzer Execution and Persistence Validation

1. Create a new `Run` record for each analyzer and vulnerable test file.
2. Execute the analyzer via its runner (e.g., `run_bandit_analyzer(run)`).
3. Refresh the `Run` instance from the database.
4. Verify:
   - The status is `Run.Status.COMPLETED`.
   - The `findings_count` equals `len(EXPECTED_FINDINGS_<TOOL>)`.
   - The `severity_counts` field is a valid dictionary.
5. Retrieve persisted findings from `findings` or related model.
6. Compare `(rule_id, line, column)` tuples against the expected findings list.
7. Assert that there are **no missing or unexpected findings**.

**Expected Result:**

- Each analyzer successfully completes execution with `Run.status = COMPLETED`.
- Findings are correctly persisted in the database.
- The persisted finding count equals the expected number of issues.
- Every expected `(rule_id, line, column)` tuple appears in the persisted results.
- No extra findings are recorded beyond the expected set.
- `severity_counts` remains a valid dictionary representing per-severity metrics.

**Post-Conditions:**

- Analyzer runs are reproducible and consistent across executions.
- All analyzers correctly detect and persist known vulnerabilities.
- Database remains synchronized with analyzer execution results.
- WebSocket updates (if active) accurately reflect persisted data.
